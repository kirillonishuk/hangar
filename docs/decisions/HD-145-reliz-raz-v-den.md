# HD-145 — 2026-11-06 — Релиз раз в день пачкой, срочный — меткой `release-now`; CI быстрее: кэши из `main`, тесты параллельно (слово владельца; меняет порядок релизов из `docs/RELEASING.md`).

Владелец: CI на PR шёл ~30 мин, и каждый merge резал релиз (~20 мин). Теперь merge сам ничего не выпускает. `release.yml` выпускает: по расписанию в 06:00 UTC, если в `main` с последнего тега `v*` есть PR без `no-release`; сразу при merge PR с меткой `release-now` (срочное); вручную (`workflow_dispatch`, bump `auto` по умолчанию); push тега `v*` — как раньше. Пачка — PR, чьи merge-коммиты лежат на first-parent линии `main` после тега (GitHub API `commits/{sha}/pulls`); bump релиза — наибольший среди них (major > minor > patch, правила PR те же: метка, иначе тип в заголовке; `no-release` не считаются; поднятый руками `Info.plist` по-прежнему главнее) — `scripts/release-bump.sh`. Release notes — список этих PR (заголовок и номер) и ссылка на полный diff вместо сгенерированного GitHub списка (в нём были бы и `no-release`). Задача `plan` (ubuntu, секунды) решает, выпускать ли, и фиксирует SHA `main`: сборка и тег берут ровно его. Группа concurrency `release` сохранена, но в неё входят только настоящие релизы: обычный merge (без `release-now`) получает свою группу и не вытесняет ждущий релиз. Релиз сначала создаётся черновиком (`--draft`); шаг «Verify the draft release» скачивает DMG и `.sha256` из черновика и роняет прогон, если не совпали sha256, `CFBundleShortVersionString` с тегом, `codesign --verify --deep --strict` или `Authority=Hangar Self-Signed`; публикуется (`--draft=false`) только проверенный черновик, провал оставляет черновик (порядок — `docs/RELEASING.md`). Приложение запускает владелец руками (релизная сборка игнорирует `HANGAR_STATE_DIR`). «Один merge за раз» теперь только для `release-now`.

CI. Причина холодного GhosttyKit (~5 мин на каждом PR): кэш, сохранённый в прогоне `pull_request`, виден только этому PR (scope `refs/pull/N/merge`), а прогона на `main` не было — общий scope пуст; Release на merge (`pull_request: closed`) кэш писать не может («Cache reservation failed: … token has no writable scopes»). Теперь CI запускается и на push в `main` — только чтобы наполнить кэши (сборка без тестов); расписанный Release тоже пишет в scope `main`. GhosttyKit — по точному ключу (`GHOSTTY_COMMIT`, `build-ghosttykit.sh`, сам action), без `restore-keys`. SwiftPM `.build` (debug с тестами и release) кэшируется из `main` с ключом «Xcode + swift --version + Package.swift + входы GhosttyKit + SHA»; PR берёт самый свежий. Чтобы кэш реально экономил компиляцию (Swift пересобирает файл, у которого mtime отличается от прошлой сборки, а checkout ставит всем «сейчас»), каждая сборка в CI ставит всем отслеживаемым файлам и GhosttyKit одно фиксированное время, а файлам, изменённым с коммита кэша (`.build/hangar-ci-commit`), — текущее. Release собирает с нуля, без этого кэша.

Тесты в CI — параллельно (по умолчанию swift-testing) вместо `--no-parallel` (так было с 2026-10-26: на 3 ядрах раннера тесты выбивали таймауты). Локально полный прогон: последовательно 572 с, параллельно 116–240 с. Пять параллельных прогонов показали ~10 тестов `HangarUITests`, которые полагались на тесное время (секунды по стене, фиксированный `sleep`, `sleep 30`-процесс, таймаут 200 мс, колбэк сразу после смены состояния): под нагрузкой главный актор стоит секундами. Починены в Tests/ — ожидание через `waitUntil` (опросы, а не стена), границы «до дедлайна» вместо «быстрее N с», процесс-долгожитель дольше теста. В CI (Swift 6.3) все цели шли одним процессом с общим пулом из 3 потоков: блокирующие ожидания UI-сьютов морили остальных больше минуты (границы «< 20 с» видели 70–85 с). Поэтому каждая тестовая цель — своим `swift test --filter '^<Target>\.'` (как локально у Swift 6.4), а границы «задолго до зависания» подняты до 120 с (зависания там 300–600 000 с). `TsLifecycleTests`, `LspLifecycleTests` (скрипт-сервер на `sh` + `sed` против 3-секундного дедлайна остановки, после которого процесс убивается и не пишет `exit`) и `DoctorChecksTests` (15-секундный бюджет login-shell пробы в коде приложения) идут отдельным шагом `--no-parallel` в конце. Один повтор на цель оставлен: на 3-ядерном раннере могут всплыть другие тесты, завязанные на время; повтор виден как warning.

**Отвергнуто:** релиз на каждый merge (долго и шумно); расписание без проверки «есть ли что выпускать» (пустые релизы); `--generate-notes` (тащит `no-release` PR); кэш `.build` по mtime из истории git (коммит PR бывает старше коммита кэша — устаревший объект прошёл бы как свежий); сохранять `.build` из каждого PR (гигабайты в лимит 10 ГБ, вытесняли бы кэш `main`).
