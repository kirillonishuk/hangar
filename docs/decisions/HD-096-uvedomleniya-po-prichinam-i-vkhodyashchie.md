# HD-096 — 2026-10-27 — Уведомления по причинам и «Входящие».

Хуки (задача 2): `claudeHooks` дополнен `PermissionRequest` без matcher (`permission-request`) и `StopFailure` без matcher — теперь по всем ошибкам, не только `rate_limit`. Хук ничего не печатает и выходит с 0, поэтому диалог разрешения идёт как обычно. На границе доверия `hangar event` и ssh-сокет (`RemoteMessage`) читают из stdin `tool_name` → `EventMessage.tool` (≤ 64 символов, иначе поле отбрасывается, событие остаётся), `tool_input.command` (только строка) → `command` (обрезается до 500), `error` → `error` (≤ 64); `message` — это `message`, а если его нет — `last_assistant_message` (текст `Stop`). В учёт лимитов Claude попадает только `StopFailure` с `rate_limit` (или ошибка без типа). Установленная интеграция до задачи 2b показывает «устарела» — набор хуков больше ожидаемого; автоматическое добавочное обновление — решение HD-095, ruling R1. Автообновление (задача 2b): при запуске (`claudeUpgradeFile` на файле из `CLAUDE_CONFIG_DIR`, как в Настройках) и при каждом подключении хоста (`ServerCheckModel.autoUpgradeClaude` — то же чтение `cat` и та же запись `remoteFileWriteScript`, что у «Применить») `claudeUpgrade` дописывает в конец событий только недостающие хуки Hangar, если интеграция уже стоит, — то есть в `hooks` есть хотя бы один обработчик `hangar`/`hangar-remote event`. Обработчик принадлежит Hangar, только если его команда — ровно `<cli> event <kind>` (три слова); всё остальное, что лишь начинается с CLI Hangar (`… && say done`, `…; afplay`, лишние аргументы), — пользовательское и не трогается. Удаляются только такие точные обработчики Hangar на событии и matcher, которые Hangar ставил раньше (`claudeHooksRetired`: `StopFailure` + `rate_limit`); группа или событие, опустевшие от этого, уходят. Вид хука считается уже есть, если в его событии любой обработчик начинается с `<cli> event <kind>` при любом matcher: так запись Hangar с matcher, изменённым пользователем (например `PreToolUse` `Task|Agent|Bash`), и составная команда остаются как есть и не дублируются (Настройки для них по-прежнему показывают «устарела»). Обработчики пользователя, `statusLine` и прочие ключи не меняются и не переставляются. Ничего не пишется, если интеграции нет (свежая установка — по-прежнему лист с diff, HD-015), если всё уже актуально (повторный запуск ничего не меняет) или если хуки Hangar указывают на другой путь CLI (приложение перенесли: смешанный набор дал бы двойные события, нужна переустановка из Настроек). Перед записью — копия `settings.json.hangar-backup-<время>` рядом с файлом, запись атомарная и отказывается, если файл изменился после чтения. Нечитаемый JSON или ошибка записи — файл не тронут, запись в лог, в Настройках / «Сервер» по-прежнему «устарела». Для обновлений это заменяет переустановку из Настроек; отдельной пометки в строке интеграции нет (только лог). `hangar-remote` — версия 4 (v3 молча отбрасывает `permission-request`). Ruling R7: `~/.hangar/bin/hangar-remote` — собственный файл Hangar, поэтому при подключении установленный скрипт более старой версии заменяется автоматически (`ServerCheckModel.autoUpgradeRemoteScript`, до хуков) той же записью `remoteFileWriteScript` — копия рядом, `cmp` с прочитанным, режим сохраняется, — затем повторная проверка сервера. Не установлен или новее — не трогается (первая установка — по-прежнему план «Сервер» с согласием). DEBUG-запуск без `HANGAR_SSH` (поддельного ssh) не обновляет на серверах ничего (`AppState.autoUpgradeRemote`). Модель (задача 3, `AgentStatus/Attention.swift`): у листа `LeafStatus.attention` — причина (`permission`, `question`, `failed`, `limit`, `done`; порядок перечисления = срочность), `tool`/`command`/`text`, `since` и `requestKey`. Источники: `Notification` `permission_prompt` → состояние «ждёт» + `permission` (текст — `message`); `elicitation_dialog` или уведомление без типа (старый claude) → `question`; прочие типы ничего не меняют; `Stop`/codex `notify` → «готово» + `done` с текстом ответа; `StopFailure` с `error` nil или `rate_limit` → «лимит» + `limit`, с любой другой ошибкой → «ошибка» + `failed` (текст — сообщение или тип ошибки); выход агента (лист claude/codex) с кодом ≠ 0 → `failed`, у шелла и прочих листьев — только точка «ошибка» без записи (`npm test` или Ctrl-C в обычном терминале — не новость, баннера и числа нет); колокол и OSC 9/777 (`desktopNotification(text:)`) у листа без хуков Claude → «ждёт» + `question` с текстом OSC. `PermissionRequest` состояние не меняет: он только запоминает инструмент и команду (`pendingPermission`), их берёт следующий `permission_prompt`, если тот пришёл не позже 30 с (`pendingPermissionTTL`), иначе разрешение без деталей (повтор того же `permission_prompt` с тем же текстом сохраняет уже взятые инструмент и команду, поэтому остаётся тем же запросом); запомненное снимают `permission_prompt`, `UserPromptSubmit`, `PostToolUse`, `Stop`, `StopFailure`, `SessionStart`, выход и перезапуск. Запись снимают активность (`UserPromptSubmit`, `PostToolUse`, `SessionStart`, начало субагента), выход с кодом 0, перезапуск/отключение хоста; фокус гасит, как и раньше, только «ждёт» листа без хуков — разрешение от хуков и `done` остаются. `done` иначе живёт до следующей активности или до «Убрать» (`StatusBoard.dismissDone` снимает только `done`, точка вкладки остаётся «готово»). `requestKey`: `StatusBoard.apply` сохраняет прежние ключ и `since`, если пришёл тот же запрос (совпадают причина, инструмент, команда, текст), иначе выдаёт новый — кнопки уведомления действуют только на свой запрос. Порядок: permission > question > failed > limit > done, внутри причины старше выше; «Входящие» — всё кроме `done` в этом порядке, затем 10 самых свежих `done`, новые сверху (ruling R2). Число Dock и колокольчика = permission + question + failed. Баннер (`shouldBanner`) — только если включены общий выключатель и причина, лист не виден, сессия не заглушена, проект не «выкл.» (при «только срочные» — лишь permission и question) и приложение не активно либо включено `notify_when_active`. `taskState` и правило чужого session id (`acceptsHook`) не менялись. Проводка (задача 5, `AppState+Attention.swift`): один список `attentionItems` (живые листья неархивных задач, порядок `sortedAttention`; у host-терминала `projectId` — id `HostShell`, `host` — его хост) питает Dock, «Входящие» и уведомления. Число Dock — `attentionCount` по листьям (раньше — задачи в «ждёт»); `dock_badge` выключает и число, и подпрыгивание. Подпрыгивание — только на новый запрос permission/question (повтор того же запроса — нет) и только если `shouldBanner` без условий видимости пропускает (общий выключатель, причина, проект не «выкл.», при «только срочные» — да, сессия не заглушена); заглушённая сессия остаётся в списке и в числе. Текст OSC 9/777 — «заголовок — тело» (пустые части выпадают) → `Attention.text`; `lastNotificationMessage` удалён, тело уведомления берётся из `Attention.text`. Колокол и OSC в ssh-шелле host-терминала дают `question` только при `ssh_terminal_bell = true`; обычный шелл проекта — никогда. Закрытые, архивированные и перезапущенные листья снимают запись (`onAttention(leaf, nil)`), «Убрать» / «Очистить» (`dismissDone`, `clearDone`) — только `done`. ⌥⌘A (`nextAttentionLeaf`) идёт по порядку «Входящих» (срочное, затем `done` новые сверху) после фокусного листа выбранной сессии, по кругу; фокус листа сообщает `onLeafSeen`. Уведомления (задача 6, `Notifier.swift`): `notice(for: AttentionItem)` — заголовок по причине («Claude просит разрешение», «Codex спрашивает», «… закончил», «…: ошибка», «… упёрся в лимит»; имя агента для листов claude/codex — «Claude»/«Codex», иначе заголовок листа), подзаголовок «Проект › сессия» (+ « · host»), тело: у разрешения `tool: command`, иначе текст внимания, иначе подпись вкладки; управляющие символы → пробел, обрезка 160 с «…». id = leafId (новое заменяет старое), `threadIdentifier` = taskId. Категории (кнопки): `permission` — «Открыть»; `permission-allow` — «Открыть», «Разрешить» (только при `allow_from_notification` и известных инструменте и команде); `question-reply` — «Открыть», «Ответить» (только лист codex: вопрос Claude — форма MCP, S5; шелл host-терминала — никогда); `open` — done, failed, вопрос Claude и host-терминала; `limit` — «Открыть лимиты» (и клик по такому баннеру, и пороговые `limit-<agent>`). «Разрешить» и «Ответить» требуют входа в систему на заблокированном экране (`.authenticationRequired`). Защита (`AppState.notificationAction`): ввод только если текущее внимание листа — та же причина с тем же `requestKey` и терминал листа `running` (для «Разрешить» ещё `allow_from_notification` и нет более нового `PermissionRequest` в ожидании — `pendingPermission`); иначе — только «Открыть», ничего не вводится. Баннер ставится на новый запрос, если `bannerAllowed` (политика `shouldBanner` + лист виден + приложение активно); снятие внимания, новый запрос без баннера и фокус листа (`onLeafSeen`, теперь и у TERMINAL-панели) убирают доставленный баннер; при запуске убираются все баннеры прошлого запуска.
