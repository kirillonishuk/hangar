# Hangar — дизайн

Дата: 2026-10-18
Статус: на ревью

## 1. Цель

Нативная замена Pane (Electron) для работы с AI-агентами на macOS.

- Меньше энергопотребления: в простое приложение почти не тратит CPU.
- Проще интерфейс: только то, что используется каждый день.
- Терминал — libghostty (GhosttyKit), рендер и поведение как в Ghostty.

**Критерий успеха:** Pane закрыт, Hangar используется каждый день; в простое (агенты не работают) процесс Hangar держит < 1% CPU и заметно меньше RAM, чем Pane на том же наборе вкладок.

### Что пользователь сказал явно

- Обязательно: несколько вкладок-агентов в задаче, статус агентов, просмотр файлов и git diff (только просмотр), ручная правка кода с LSP.
- Агенты: Claude Code и Codex.
- Правка кода — терминальный редактор (Helix, опционально Neovim) во вкладке libghostty.
- Структура: проект → задачи → вкладки; worktree у задачи — опционально.
- CLI и MCP для управления приложением — сразу, в первой версии.
- После закрытия и повторного открытия восстанавливаются все задачи и вкладки.
- Агент по умолчанию — claude, меняется в настройках.
- Визуальный стиль — «Ghostty-native» (тёмный, плотный), сайдбар на всю высоту, вкладки — внутри области задачи.

### Допущения

- Только macOS 14+, Apple Silicon.
- Тема, шрифт и клавиши терминала берутся из конфига Ghostty пользователя (`~/.config/ghostty/config`).
- Миграции данных из Pane нет.
- Горячие клавиши `⌘…` работают в любой раскладке, включая русскую (сопоставление по keyCode, а не по символу).

### Вне рамок первой версии

Git-действия (stage/commit/push/PR), встроенный браузер, собственный редактор кода, онбординг, синхронизация, Linux/Windows.

## 2. Архитектура

Swift (AppKit + SwiftUI), один Swift Package с модулями и Xcode-проект приложения. Рядом — CLI-бинарник `hangar`.

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `GhosttyBridge` | Обёртка над C-API GhosttyKit: app/surface lifecycle, ввод, события (title, bell, desktop notification, child exit), чтение текста экрана, пауза рендера. Единственное место, знающее про нестабильный API. | GhosttyKit.xcframework |
| `Workspace` | Модель Project → Task → Tab (+ сплиты), сериализация в JSON, восстановление. Чистая логика. | — |
| `Git` | Вызов `git` CLI: default branch (`origin/HEAD`), список веток, `fetch`, `worktree add/remove`, `status --porcelain=v2`, `diff`. | git |
| `AgentStatus` | Приём событий агентов, свёртка в статус вкладки и задачи. | — |
| `Usage` | Лимиты подписок: приём `rate_limits` от `hangar statusline`, вызов `codex app-server`, свёртка в окна, пороги. | `ControlServer`, `Exec` |
| `Integration` | Правка файлов агентов (`~/.claude/settings.json`, `~/.codex/config.toml`): показ diff, копия, запись, откат (#43). | — |
| `Power` | Блокировка сна, пока есть вкладки в `working` (число работающих передаёт UI). | IOKit |
| `Exec` | «Где выполнять»: локально (`Process`) или на SSH-хосте (через общий мастер-процесс `ssh -M` без `ControlPersist`, #47). Через него ходят `Git`, `Usage`, запуск вкладок. | ssh |
| `ControlServer` | Unix-сокет, JSON-протокол (запрос/ответ, по строке на сообщение). Обслуживает hooks, CLI и MCP. Этап 3 — типы `event` и `usage`; этап 5 — запросы/ответы (#45). | `Workspace`, `AgentStatus` |
| `UI` | Окно, сайдбар, полоса вкладок, сплиты, инспектор, diff-вкладка, лист новой задачи, настройки. | все выше |
| `hangar` (CLI) | Подкоманды CLI + `hangar mcp` (MCP-сервер со stdio). Ходит в сокет. | протокол `ControlServer` |

Сборка GhosttyKit: скрипт `scripts/build-ghosttykit.sh` клонирует Ghostty на закреплённом коммите и собирает xcframework через Zig. Обновление Ghostty = смена коммита + правки только в `GhosttyBridge`.

Данные: `~/Library/Application Support/Hangar/state.json` (состояние), сокет `~/Library/Application Support/Hangar/hangar.sock`, конфиг `~/.config/hangar/config.toml`.

## 3. Модель данных

- **Project**: id, имя, путь к репозиторию, последняя выбранная базовая ветка, worktree по умолчанию (вкл/выкл), папка worktree (необязательно; сюда идут все worktree проекта), список «копировать в worktree» (игнорируемые пути/маски) и команда после создания; без своего списка — по lockfile (pnpm/yarn/bun: `.env*` и т. п., npm: ещё клон `node_modules`); команда install по lockfile только предлагается и выполняется лишь сохранённой в проекте — #58.
- **Task**: id, имя, project id, режим (`main-folder` | `worktree`), путь worktree, ветка, базовая ветка, порядок, архивирована ли.
- **Tab**: id, task id, тип (`claude` | `codex` | `editor` | `shell` | `diff`), заголовок, дерево сплитов (каждый лист — surface со своим типом), `agentSessionId` (для resume), cwd, открытый файл (для editor).
- Diff-вкладка временная: не сохраняется и не восстанавливается.

## 4. Интерфейс

Дизайн-система: `docs/design/DESIGN.md`. Эталонные макеты: `docs/superpowers/mockups/style-a-v2.html` (основной экран, diff), `new-task-v4.html` (новая задача), `style-a-screens.html` (уведомление, ранние варианты).

- **Сайдбар** (на всю высоту, светофор над ним): «+ Новая задача», закреплённые, проекты (сворачиваемые группы) → задачи, архив; у задачи — точка статуса или иконка worktree. Ширина перетаскиванием сохраняется; `⌘0` сворачивает в рейку 44 с монограммами (решения #32, #35).
- **Область задачи**: строка заголовка «Проект · Задача» по центру и кнопка инспектора справа; ниже — вкладки со статус-точкой и иконкой агента, `+` (меню: Claude, Codex, Helix, Shell). Сплиты как в Ghostty (`⌘D`, `⌘⇧D`).
- **Инспектор** справа (`⌘⌥I` скрыть/показать), сегменты `Files` / `Changes N`.
  - Files: дерево файлов (с учётом `.gitignore`), бейдж M/A/D. Клик — открыть в Helix: в существующей editor-вкладке задачи (через отправку `Esc` + `:open path` в Helix), иначе в новой.
  - Changes: изменённые файлы. Клик — временная diff-вкладка (курсивом); следующий клик заменяет её. По умолчанию diff относительно merge-base с базовой веткой, `⌥B` — только незакоммиченное (при активной diff-вкладке; иначе — клик по подсказке под Changes). `↑/↓` — соседний файл, `Enter` — открыть в Helix на строке. Подсветка синтаксиса отложена (#44).
- **Строка состояния** (внизу области задачи, DESIGN.md «Строка состояния»): ветка worktree, `+N −M · K файлов`, у удалённой задачи — хост, статус активного агента; клик по счётчикам — Changes.
- **Новая задача** (`⌘N`): название; карточка настроек: Worktree (переключатель), От ветки (выпадающий список с поиском: сначала remote, по умолчанию из `origin/HEAD`; затем локальные), Новая ветка (из названия: само название, если в нём есть `/` и это допустимое имя ветки вроде `feat/JS-13333`, иначе slug — #48; редактируемая); поле «Первое сообщение для claude». Без worktree строки веток неактивны, внизу — текущая ветка. Перед созданием worktree — `git fetch`; подробности (fetch, валидация `check-ref-format`, ошибка «ветка уже существует», не-git проект — строк worktree нет) — решение #42. После создания worktree в него клонируются игнорируемые файлы из списка проекта (прогресс «Копирую node_modules…» в подвале), строка «После создания: <команда>» с переключателем (предложенная по lockfile — выключена; включил — сохраняется в проект), команда и ошибки копирования — во второй вкладке shell в корне worktree (#58). Настройки проекта: имя, путь, ветка по умолчанию, папка worktree (с подсказкой «сюда создаются все worktree»), «Копировать в worktree», «Команда после создания».
- **Архив** (`⌘⇧W`, меню задачи; #57): задача без worktree просто уходит в архив. У задачи с worktree вкладки останавливаются (удалённые tmux-сессии убиваются), папка worktree удаляется (атомарный `mv` в `<путь>.hangar-removing`, `git worktree prune`, удаление в фоне; оставшиеся после выхода надгробия убираются при запуске — #NN-crash-safe-archive), ветка остаётся. Незакоммиченные изменения или файлы вне git (`.env`) — сначала подтверждение со списком, как при удалении. Удалённый проект — то же на сервере; хост не подключён — отказ, ничего не меняется. «Восстановить» и «Отменить» в тосте заново создают worktree, если по пути нет рабочего worktree (`rev-parse`; неполная папка убирается), из ветки (`git worktree add <путь> <ветка>`) и открывают вкладки; ветки нет — ошибка и предложение восстановить задачу в папке проекта.
- **Быстрый переход** `⌘K` / `⌘P`: задачи и файлы.
- **Клавиши**: `⌘1…9` вкладки, `⇧⌘[`/`⇧⌘]` задачи, `⌘N` задача, `⌘T` вкладка (shell), `⌘W` закрыть вкладку, `⌘D`/`⇧⌘D` сплит, `⌘0` сайдбар, `⇧⌘N` проект, `⌥⌘I` инспектор, `⌥⌘1`/`⌥⌘2` инспектор на Files/Changes, `⌥⌘R` открыть в Finder, `⌥⌘C` скопировать путь. Полная таблица — DESIGN.md «Тултипы и клавиши».
- **Настройки**: короткий экран + `config.toml` (`default_agent`, команды агентов и их аргументы, редактор `hx`/`nvim`, `terminal_background` = `hangar`/`theme`, уведомления вкл/выкл, `keep_awake` — «не засыпать», §5.2).

## 5. Статусы агентов

Статусы: `working`, `waiting`, `done`, `failed`, `idle`.

Каждая surface стартует с env `HANGAR_TAB_ID`, `HANGAR_LEAF_ID` (статус хранится на лист; событие с tab, не владеющим leaf, игнорируется), `HANGAR_SOCKET` и `HANGAR_PORT` — порт задачи (#NN-port: стабильный, из id задачи в 41000–48999, уникальный среди задач, хранится в модели; локально и на сервере; в меню задачи «Порт: N (копировать)»). `hangar event <kind> [--session <id>]` отправляет событие; без `HANGAR_TAB_ID` молча выходит с кодом 0 (не ломает агентов вне Hangar).

- **Claude Code**: Hangar предлагает (с подтверждением и показом diff) добавить hooks в `~/.claude/settings.json`: `SessionStart` (id сессии), `UserPromptSubmit` → working, `PostToolUse` (matcher `*`) → working, `Notification` → waiting только для `permission_prompt`/`elicitation_dialog` (`idle_prompt` не трогает статус), `Stop` → done, `StopFailure` matcher `rate_limit` → failed + `limitReached`; у каждого `"timeout": 5` (#43). `session_id` из payload hook сохраняется в листе.
- **Codex**: `notify` в `~/.codex/config.toml` → done (+ session id). `waiting` — по bell/OSC-уведомлению от surface. Точность проверяется на практике и дорабатывается.
- **Запасные пути (#43)**: bell/OSC-уведомление → waiting только у листов claude/codex и только если у листа не было hook Claude; гаснет в idle при фокусе листа.
- **Все**: выход процесса с кодом > 0 → failed, иначе idle; перезапуск → idle.
- **Статус задачи** = максимальный из вкладок по приоритету waiting > failed > working > done > idle.
- **Уведомления macOS** — при переходе в waiting/done, если вкладка не видна. Клик открывает задачу и вкладку.

## 5.1 Лимиты подписок

Макет: `docs/superpowers/mockups/limits.html`.

**UI.** Внизу сайдбара — строка на каждого агента (claude, codex): две полоски (окно 5 ч и неделя) и максимальный процент. Клик или `⌘⇧L` — поповер: план, каждое окно (у Claude — все пришедшие окна, включая отдельные недельные по моделям, если они есть), процент, время сброса, «обновлено N мин назад», кнопка ↻. Пороги: ≥ 80% — жёлтый и «почти лимит», ≥ 95% или исчерпан — красный и «лимит исчерпан». Если лимит агента исчерпан, точки его вкладок тоже красные. Уведомление macOS — один раз при пересечении 80% и при исчерпании окна (выключается в настройках). Строка агента не показывается, если данных нет (агент не установлен, вход по API-ключу).

**Модель.** `UsageWindow { kind: session | weekly | weekly_model(name), usedPercent, resetsAt, updatedAt }`, по агенту — список окон, план и флаг `limitReached`. Окно с прошедшим `resetsAt` сбрасывается в 0% (ожидаем свежие данные). Все поля во входных данных опциональны.

**Claude — только документированные источники:**
- Статус-лайн. Hangar (с согласия, как и hooks) прописывает `statusLine` = `hangar statusline`. Команда читает JSON из stdin, отправляет все окна `rate_limits` — `five_hour`, `seven_day` и недельные по моделям `seven_day_<model>` (`used_percentage`, `resets_at`) — в сокет, затем вызывает исходную статус-лайн пользователя (если была) с тем же stdin и печатает её вывод. Исходная команда хранится в самой команде: `'<cli>' statusline --then '<исходная команда>'`, остальные ключи `statusLine` не трогаются; откат восстанавливает её оттуда. Путь CLI — `Hangar.app/Contents/Helpers/hangar` (#43). Данные приходят только для Pro/Max и только пока в какой-то вкладке работает claude, поэтому показываем возраст данных.
- Исчерпание: hook `StopFailure` с matcher `rate_limit` → `limitReached`.
- Недокументированный OAuth usage endpoint не используем.

**Codex:**
- Основной: `codex app-server` (JSON-RPC по stdio), метод `account/rateLimits/read` → окна `{usedPercent, windowDurationMins, resetsAt}`. Процесс короткоживущий: запускается при открытии поповера, по ↻ и после события «ход закончен» (не чаще раза в минуту), затем завершается. Окна различаем по `windowDurationMins` (300 — сессия, 10080 — неделя), а не по позиции.
- Резервный: последнее событие `token_count` с `rate_limits` в свежем rollout-файле `~/.codex/sessions/**` (форматы ≥ 0.48; если событий нет — источник пропускается).
- Исчерпание: ошибка `UsageLimitExceeded` / текст «You've hit your usage limit» → `limitReached` до `resetsAt`.
- Недокументированный `/wham/usage` не используем.
- Примечание: `notify` в Codex помечен как legacy. Если у установленной версии есть новые hooks (`~/.codex/hooks.json`), статусы и триггер обновления лимитов берём из них, `notify` — запасной путь. Проверяется в спайке.

## 5.2 Не засыпать, пока агенты работают

- Включается переключателем в настройках и иконкой ☕ в строке внизу сайдбара (по умолчанию включено). Иконка подсвечена, когда блокировка активна; тултип — сколько агентов работает.
- Пока есть хотя бы одна вкладка в `working` (локальная или удалённая) — держим `IOPMAssertion` `PreventUserIdleSystemSleep` с фиксированным английским именем «Hangar: 1 agent working» / «Hangar: N agents working» (`pmset` не показывает кириллицу, #46). Экран может гаснуть.
- Снятие — через 2 минуты после того, как `working`-вкладок не осталось (чтобы не дёргать между ходами). Таймер снятия — единственный: взводится на переходе «работающих стало 0» при удерживаемой блокировке; в простое без блокировки таймеров нет (#45). Выключение фичи или выход из приложения снимает сразу.
- Работа с закрытой крышкой без внешнего монитора и питания не поддерживается (нужен root, `pmset disablesleep`) — не делаем.

## 6. Сохранение и восстановление

- Состояние пишется на диск при изменениях (debounce 500 мс) и при выходе; запись атомарная (temp + rename).
- При запуске восстанавливаются проекты, задачи, порядок, вкладки, сплиты, активная задача и вкладка, состояние инспектора.
- Вкладки:
  - claude → `claude --resume <sessionId>`; без `sessionId` → `claude --continue` в cwd (подтверждено спайком);
  - codex → `codex resume <sessionId>`, если id нет — `codex resume --last` в cwd задачи;
  - editor → редактор с тем же файлом;
  - shell → новый shell в том же cwd.
- Процессы не переживают выход. `⌘Q` при наличии вкладок в `working` спрашивает подтверждение.
- Повреждённый `state.json` (и висячий симлинк на него) → перенос в `state.json.bak`, старт с пустым состоянием и предупреждение.

## 7. CLI и MCP

`hangar` (протокол — JSON по Unix-сокету):

| Команда | Действие |
|---|---|
| `hangar projects list` / `add <path> [--host H]` | проекты (с `--host` — папка на сервере, #45) |
| `hangar tasks list [--project]` | задачи со статусами (и лист панели TERMINAL — его id годится как `--tab`) |
| `hangar tasks create --project P --name N [--worktree --base B] [--prompt T]` | создать задачу |
| `hangar tabs open --task T --kind claude\|codex\|editor\|shell [--prompt T]` | новая вкладка |
| `hangar tabs send --tab ID [<text>] [--enter] [--key K]…` | вставить текст, затем нажать клавиши (`enter`, `escape`, `tab`, `backspace`, `up`, `down`, `left`, `right`, `ctrl-c`, `ctrl-d`) |
| `hangar tabs read --tab ID [--lines N]` | последние N строк экрана (по умолчанию 100) |
| `hangar tasks archive --task T --yes [--force]` | архивировать; worktree удаляется, ветка остаётся (#57); грязный worktree или ignored-файлы — отказ без `--force` (MCP `force: true`) |
| `hangar event <kind>` | событие от hooks |
| `hangar mcp` | MCP-сервер (stdio) с теми же операциями |

Разрушительные операции без `--yes` (в MCP — `yes: true`) отклоняются. Все команды поддерживают `--json`.

- Ссылки (`--project`, `--task`, `--tab`): полный UUID, уникальный префикс id (≥ 4 символов) или имя (вкладки — только id); неоднозначность — ошибка со списком id (#45).
- Коды выхода: 0 — успех; 1 — ошибка приложения, Hangar не запущен, таймаут; 2 — ошибка использования или нет `--yes`. С `--json` результат — JSON в stdout, ошибка — `{"error":{"code","message"}}` в stderr.
- Вывод CLI и MCP — английский (машинный интерфейс, вне `L10n`).
- MCP подключается командами `claude mcp add --scope user hangar -- '<cli>' mcp` и `codex mcp add hangar -- '<cli>' mcp`; настройки показывают их с кнопкой «Скопировать», конфиги агентов Hangar не правит.

## 8. Ошибки

- Нет git / не репозиторий → проект без Changes и worktree.
- Ошибка `git fetch`/`worktree add` → лист новой задачи не закрывается, показывает stderr git.
- Нет коммитов → worktree недоступен. Fetch не прошёл → stderr + кнопка «Создать без fetch».
- Hooks не установлены → статусы только по bell/exit, в настройках — предупреждение с кнопкой установки.
- Сокет занят (второй экземпляр) → по успешному `connect` активировать существующий экземпляр (pid собеседника, `LOCAL_PEERPID`), новый процесс выходит; мёртвый сокет удаляется (#43).
- Агент не найден в PATH → вкладка показывает сообщение и команду установки.

## 11.1 SSH-проекты (этап 6)

Архитектура закладывается с этапа 1: все команды идут через `Exec`, проект хранит `location: local | ssh(host, path)`.

- **Локальный диск** (этап 6): у удалённого проекта путь никогда не читается с Mac — git, `lastFetch`, «есть ли папка» при удалении worktree и в настройках проекта идут через `Runner` хоста (`AppState.runner(for:)` / `git(for:)`; без соединения — сразу `notConnected`); подбор имени ветки не проверяет папку worktree (её занятость сообщит `git worktree add`); `~` в путях не раскрывается. Серость проекта и `exists` в `projects list` — по состоянию хоста (`unreachable`), не по диску; `ProjectInfo.host`, человеческий вывод `<host>:<path>`. «Открыть в Finder» и внешний редактор для удалённых выключены, «Скопировать путь» даёт `host:path`. Удаление worktree: проверки (папка, незакоммиченное, ignored-файлы) — на сервере; проверка, которая не ответила, останавливает удаление с ошибкой (не считается «чисто» или «папки нет»). Так же хост без соединения не выглядит как «не репозиторий» (лист «Новая задача» пишет «Нет соединения с <host>», `tasks.create` — `host <host> is not connected`) или «папка не найдена» (настройки проекта).
- **Добавление проекта**: «+ проект» → «Удалённый» → хост из `~/.ssh/config` (или `user@host`) и путь. Аутентификация — через системный ssh и агент ключей; пароли Hangar не хранит.
- **Подключение** (#47): один мастер на хост — дочерний процесс Hangar `ssh -M -T -S <cp> -o ControlPersist=no -o BatchMode=yes`; удалённая сторона печатает `HANGAR-READY <$HOME>` и ждёт на stdin. Готовность — маркер, обрыв — выход процесса (без опроса `-O check`). `ControlPath` в `<state>/ssh/`, при длинном пути — `/tmp/hangar-<uid>/`. Все вкладки, git и служебные команды переиспользуют его; команды идут с PATH логин-шелла, который увидела проверка сервера (там же она нашла `git` и `tmux`). Только системный ssh и конфиг пользователя; пароль и 2FA в фоне не поддерживаются — подсказка выполнить `ssh <host>` в Терминале.
- **Проверка и установка окружения** при каждом подключении (молча, одна команда через мастер) и по кнопке «Проверить сервер»: определяем ОС и пакетный менеджер, проверяем `git`, `tmux`, `claude`, `codex`, `hx`, скрипт `hangar-remote` и интеграции (hooks, statusline). Показываем список «есть / нет / версия» и план установки с точными командами; устанавливаем только после подтверждения пользователя (sudo — его пароль вводится в терминальной вкладке, Hangar его не видит). Отсутствующий необязательный инструмент (например `hx`) не блокирует работу.
- **Вкладки** (#47): каждый удалённый лист — сессия tmux `hangar-<leafId>` на сервере; surface запускает `ssh -t host tmux new -A -s hangar-<leafId> …`. Агенты переживают обрыв связи и сон Mac. Код выхода 255 — сессия не закончилась (обрыв или detach): лист не `failed` и не закрывается, ↩ и переподключение делают `reattach` к той же сессии; собственный код агента 255 превращается в 254. Код 0 — лист закрывается, как локальный. Закрытие листа/вкладки, архив и удаление задачи убивают сессию, выход из Hangar — нет. Если tmux поставить нельзя — обычный `ssh -t`, восстановление через `claude --resume` / `codex resume`.
- **Статусы и лимиты** (#47): на сервер пробрасывается не основной сокет, а отдельный сокет хоста (`mkdir -p -m 700 ~/.hangar/run && rm -f ~/.hangar/hangar.sock`, затем `ssh -S <cp> -O forward -R <home>/.hangar/hangar.sock:<state>/ssh/r-<id>.sock`; `<home>` — из `HANGAR-READY <$HOME>`, sshd `~` не раскрывает). В сессию передаются `HANGAR_TAB_ID`/`HANGAR_LEAF_ID`/`HANGAR_SOCKET=<home>/.hangar/hangar.sock`. Он принимает только `hook`/`statusline`, одно сообщение на соединение и события только для листов проектов этого хоста. `hangar-remote` — POSIX sh-скрипт (без Swift-бинарника) с тем же argv, что `hangar event` / `hangar statusline`; JSON в sh не разбирается — заголовок + сырые байты, разбор в Swift на Mac. При обрыве события теряются, статусы сохраняются до переподключения.
- **Файлы и diff**: `git ls-files`, `git status --porcelain=v2`, `git diff` через `Exec`; обновление — при показе задачи, когда окно становится key, после `done` агента и после переподключения хоста, если инспектор показывал «нет соединения» и виден (FSEvents удалённо нет; скрытый загрузится при показе), без таймеров. Хост не подключён — одна спокойная строка «Нет соединения с <host>» вместо ошибки git; удалённая папка без git — «дерево файлов недоступно» (без листинга каталога).
- **Worktree** — `git worktree add` на сервере; Helix запускается на сервере (LSP рядом с кодом).
- **Ошибки**: хост недоступен → задачи проекта серые с «переподключиться»; обрыв — автопереподключение с backoff 2, 4, 8, 16, 32, 60… с, не больше 10 попыток, только пока приложение активно или у хоста были `working`-листья; после пробуждения — одна проба с таймаутом 10 с (#47).
