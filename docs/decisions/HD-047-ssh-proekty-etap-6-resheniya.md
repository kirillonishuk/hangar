# HD-047 — 2026-10-23 — SSH-проекты (этап 6), решения плана.

§11.1 и HD-019–HD-021 оставляют открытыми механику мастера, проброса, протокол `hangar-remote`, коды выхода вкладок и правила переподключения; выбраны простейшие полные варианты:
- Транспорт: только `/usr/bin/ssh` и конфиг пользователя как есть; фоновые вызовы с `BatchMode=yes` и `ConnectTimeout=10` (без мастера ssh идёт напрямую, мёртвый хост должен отказать быстро). Ошибка входа (ключ хоста не принят, ключ не в агенте, нужен пароль) → сообщение со stderr и подсказка «выполните `ssh <host>` в Терминале, затем «Переподключиться»». Пароль, 2FA и askpass не поддерживаем (отложено). `shellQuote` выносит `\` за одинарные кавычки (`'\\'`): логин-шелл сервера может быть fish, а он читает `\'` внутри кавычек как кавычку — иначе аргумент `a\'; cmd` исполнился бы. Слово с `=` в начале тоже берётся в кавычки: zsh раскрывает `=cmd` в путь команды.
- Мастер: `ssh -M -T -S <cp> -o ControlPersist=no -o BatchMode=yes -- <host> '/bin/sh -c …'`. Удалённый скрипт печатает `HANGAR-READY <$HOME>` и делает `exec cat >/dev/null`; stdin мастера — труба, которую держит Hangar. Готовность — маркер в stdout, обрыв — выход процесса, при выходе — `-O exit`. Почему: фоновый `ControlPersist` не даёт события смерти, а `-O check` — это опрос. Заменяет «ControlPersist» в §11.1. Путь `<state>/ssh/cm-<fnv64 hex>`; если вместе с суффиксом ssh (17 байт) он длиннее 104 байт — `/tmp/hangar-<uid>/cm-<…>`.
- Проброс: после готовности `mkdir -p -m 700 ~/.hangar/run && rm -f ~/.hangar/hangar.sock`, затем `ssh -S <cp> -O forward -R <home>/.hangar/hangar.sock:<state>/ssh/r-<id>.sock`. `rm` нужен потому, что для `-R` действует `StreamLocalBindUnlink` sshd, а он по умолчанию `no`. Отказ (`AllowStreamLocalForwarding no`) → предупреждение «статусы недоступны», вкладки работают.
- Сокет хоста — отдельный `ControlServer` в режиме remote: только `hook`/`statusline`, одно сообщение на соединение, события — только для листов проектов этого хоста. Почему: проброшенный сокет доступен любому процессу этой учётной записи на сервере; основной сокет позволил бы взломанному серверу печатать в локальные терминалы (`tabs send`).
- `hangar-remote` (версия 1, `~/.hangar/bin/hangar-remote`) принимает тот же argv, что `hangar event` / `hangar statusline`, поэтому `claudeInstall`/`codexInstall(cli:)` переиспользуются. JSON в sh не разбирается: заголовок + сырые байты payload, разбор — в Swift на Mac. Клиент сокета — первый найденный из `python3`, `socat`, `nc -U`; если нет ни одного, статусов нет, а проверка предлагает поставить `socat`.
- Вкладки: одна tmux-сессия на лист, `hangar-<leafId>` (статус хранится на лист, HD-043; «tabId» в §11.1 написан до HD-043). Код 255 означает «сессия не закончилась» (обрыв или detach): лист не `failed` и не закрывается, ↩ и переподключение делают `reattach` (агенты возобновляются, первое сообщение не повторяется). Код 0 — лист закрывается, как локальный; собственный код агента 255 превращается в 254. В сессии выключается `status`. Закрытие листа или вкладки, архив и удаление задачи убивают сессии, выход из Hangar — нет. Для ssh задаётся `TERM=xterm-256color`. Агенты на сервере запускаются как `claude`/`codex` (локальные `[agents]` — пути Mac), редактор — `config.editor`. Без tmux — прямой `ssh -t`, восстановление через `--resume`/`resume`. Механика: локально `/bin/sh -c` (ssh — абсолютный путь) с обёрткой OSC 133, `ssh -t -e none` (`~.` в начале строки не рвёт связь). Значения (папка, имя сессии, файл кода `~/.hangar/run/<имя>.exit`, `HANGAR_*`, команда агента) идут на сервер словами в кавычках и через переменные окружения проходят логин-шелл (fish не знает `"$@"`), скрипт — всегда `/bin/sh`; перед `tmux` переменные снимаются, чтобы не осесть в глобальном окружении tmux-сервера. Все сессии — на отдельном tmux-сервере `tmux -L hangar` (создание, attach, `has-session`, `kill-session`): `tmux kill-server` пользователя и прочие действия с сервером по умолчанию агентов не трогают; `tmux.conf` пользователя при этом действует. Команда pane передаётся tmux как argv (tmux ≥ 3.0 исполняет её без `default-shell`, который может быть fish); `-c` не передаётся — tmux раскрывает в нём форматы (`#`, `;`), папку pane берёт от `cd` скрипта. Порядок без гонки: сначала `attach -d -t =<имя>` (новый клиент отключает прежний — зависшее старое соединение не прочтёт код); только если attach не удался, сессии нет и файл кода окончателен — агент уже вышел (возможно, без клиента): код возвращается, новая сессия не создаётся; иначе `new-session -A -D` (для гонки двух клиентов). Пустой или нечисловой файл — 254 («код потерян»), не успех. Связка «`has-session` → `rm` → `new-session`» отвергнута: код, записанный между шагами, терялся, а агент стартовал заново. `status off` ставится с целью `=<имя>:` (голое `=<имя>` tmux читает как pane, и опция не ставилась). Известные ограничения: `remain-on-exit` / `destroy-unattached` в `tmux.conf` пользователя и строка в rc вида `[ -z "$TMUX" ] && exec tmux`. Пока хост не подключён, лист ждёт (`notConnected`) и стартует по `onConnected` со своим исходным контекстом; reattach не сбрасывает статус агента.
- Проверка сервера идёт при каждом подключении (одна команда через мастер), молча. Логин-шелл сервера (может быть fish) даёт только PATH и окружение: скрипт проверки передаётся ему в переменной `HANGAR_CHECK` и всегда исполняется `/bin/sh`. Вывод проверки недоверенный: строгий разбор с лимитами, план установки строится только из фиксированной таблицы; `helix` ставится только там, где он есть в репозиториях дистрибутива (`pacman`, `apk`, `brew`, `dnf` на Fedora), иначе `hx` уходит в ручные. Команды в терминальном скрипте — отдельными строками (`set -e` не останавливается на левой части `&&` и на `curl | bash`): `apt-get update` и `install` раздельно, установщик Claude сначала скачивается во временный файл. `hangar-remote` пишется в `.tmp` и переименовывается. Одно правило PATH для всех команд: проверка печатает и `$PATH` логин-шелла (строгий разбор: ≤ 4000 байт, печатные символы, только абсолютные элементы, иначе не используется), он хранится в отчёте, и каждая команда через `RemoteHosts.runner` (git, `kill-session`, `cat` интеграций) получает его отдельным аргументом `remoteRunScript`; до первой проверки — PATH, который даёт sshd. Вывод любой такой команды ограничен 64 MiB на поток (ssh убивается). Логин-шелл csh/tcsh на этом этапе не поддерживается: если отчёта нет, одна проба `$SHELL` даёт ошибку `unsupportedShell`. Лист открывается сам только при добавлении проекта. Если обязательного не хватает или `hangar-remote` устарел, в строке хоста сайдбара — предупреждение. Пакеты ставятся во вкладке-терминале внутри листа. `hangar-remote` и файлы интеграций пишутся через stdin ssh после того же подтверждения; интеграции — каждая через свой лист diff. Методов установки в CLI/MCP нет.
- Статусы: удалённые листья входят в `workingLeafCount`. При обрыве статусы сохраняются, переподключение — backoff 2, 4, 8, 16, 32, 60, 60… с, не больше 10 попыток, только пока приложение активно или у хоста были `working`-листья (иначе пауза до активации); после отказа хост «недоступен», его листья `idle`. После пробуждения — одна проба `true` с таймаутом 10 с на каждый подключённый хост. Проверка сервера при подключении — с таймаутом 30 с и лимитом вывода 256 KiB (ssh убивается). Пока хост не подключён, `RemoteHosts.runner` сразу отвечает ошибкой `notConnected`, а не звонит ssh напрямую. Попытка, отложенная до активации, делается сразу при `didBecomeActive`. После `.auth` и `.unsupportedShell` переподключения нет. ⌘Q спрашивает только про локальные и не-tmux удалённые `working`.
- Инспектор: git через `Runner.ssh` (`GIT_TERMINAL_PROMPT=0`; `GIT_SSH_COMMAND` = значение пользователя, иначе `ssh -o BatchMode=yes`). Обновление — при показе задачи, при `didBecomeKey` окна и по `done`. Не-git удалённая папка — без дерева. `lastFetch` — `date -r` через `Runner`. Проверка папки worktree при подсказке ветки для удалённого проекта пропускается (`worktree add` сам сообщит).
- *Заменено HD-081.* Helix на сервере: после `Esc` пауза 600 мс (у tmux `escape-time` по умолчанию до 500 мс).
- UI (задача 9): закрытие/архив/удаление удалённого листа при неподключённом хосте ставит `kill-session` в очередь хоста, она уходит по `onConnected`; `kill-session`, который не дошёл до tmux (ошибка runner или код 255 от ssh), снова встаёт в очередь хоста (очередь только в памяти: выход или удаление хоста офлайн оставляют сессии на сервере). Ушёл последний проект хоста — сначала его сессии, затем `remote.remove(host)`; офлайн-хост удаляется сразу. Лист «Удалённый проект» отпускает подключённый им хост, если проект не добавлен. Лист «Сервер» без соединения сначала подключается. Пауза повтора без таймера показывается «нет связи». Установка: команды плана показываются дословно, терминал запускает ровно `terminalScript` подтверждённых шагов, `hangar-remote` пишется только после успешного выхода терминала. Интеграции на сервере: `cat` файла, diff, запись скриптом через stdin ssh (сверка `cmp` с прочитанным, иначе код 3 «файл изменился»; `cp -p` в `.hangar-backup-<время>`; временный файл с прежними правами и `mv`); симлинки разворачиваются. Локальные `~/.claude`/`~/.codex` не затрагиваются.
- Отвергнуто: `ControlPersist` в фоне; опрос `-O check`; проброс основного сокета; askpass-диалог; Swift-бинарник и разбор JSON в sh; установка terminfo Ghostty на сервер; правка `~/.ssh/config`.
