# Подчаты (сабсессии) — спека

Статус: решения владельца от 2026-11-04 (п. 1–5 ниже; дополнение того же дня — ручное создание, экономия токенов) — решение #128; **пересмотр владельца того же дня — решение #131**: подчат никак не влияет на родителя (в терминал родителя ничего не печатается), по умолчанию работает в папке родителя, о конце сообщает только уведомление пользователю. Обязательны: дизайн-система (`specs/2026-10-30-design-system.md`, #112), словарь (#113), чаты без проекта (`specs/2026-10-31-free-chats-design.md`, #126), статусы агента (#43, #95, #119), CLI/MCP (#45, #73).

## 1. Что это
**Подчат** — способ сделать что-то **параллельно**: полноценный чат со своим терминалом и агентом, под родителем в сайдбаре. Создаётся руками (лист, меню, ⇧⌥⌘N) или агентом через MCP / CLI (`sessions_spawn`). Подчат **никак не влияет на родителя**: в терминал родителя Hangar ничего не печатает (#131). Когда подчат **полностью** закончил — агент остановился и не осталось фоновых задач, которые он запустил, — пользователь получает уведомление, в сайдбаре — статус подчата. Агент родителя, если хочет итог, сам спрашивает его `sessions_wait` (по запросу, без побочных эффектов). Пример владельца: подчат делает релиз, всё запускает, оставляет фоновый shell, ждущий выкладки; «закончил» — только после того, как этот shell закончился.

Слова: в API — sub-session (`sessions_spawn`, `sessions_wait`, поле `parent`); в интерфейсе по словарю #113 — «подчат» / "sub-chat" (слово «сабсессия» запрещено тестом словаря: в ru нет «сесси», в en нет "session").

Зачем ещё: «найди X / сделай Y» рядом, в той же папке, не тратя контекст основного чата.

## 2. Модель (`Sources/Workspace`)
- `HangarTask.parentTaskId: UUID?` — ключ `parentTaskId`, `decodeIfPresent` (старые файлы читаются; откат на старую сборку теряет только связь — подчаты становятся обычными чатами).
- `HangarTask.subsCollapsed: Bool` — свёрнут ли список подчатов под родителем (ключ `subsCollapsed`, по умолчанию развёрнут).
- **Где работает (#131):** по умолчанию — **в папке родителя**: тот же worktree (или основная папка), в которой работает родитель, — оба чата в одной копии (`addSubSession(mode: nil)` берёт `mode` родителя; новой копии и команды подготовки нет). По выбору — новый worktree (лист: только у локального чата проекта; MCP/CLI `worktree`, как `sessions_create`). Чат без проекта → новый чат без проекта (своя запись `FreeChat`) в той же общей папке `Chats`; worktree нельзя. Выбор в сайдбаре не меняется.
- Общая папка: `WorkspaceState.worktreeSharers(of:openOnly:)` — другие сессии проекта в том же worktree. Строки состояния — одна запись на папку (файл переопределения общий, сама строка считается по stdin агента, у каждого своя).
- `WorkspaceState.subSessions(of:)` — незаархивированные дети по `order`; `hasLiveParent(_:)` — родитель существует и не в архиве (иначе подчат показывается как обычный чат верхнего уровня).
- Вложенность любой глубины (подчат подчата), отступ в сайдбаре — до двух уровней.

## 3. Сайдбар
- Подчаты не стоят в общем списке проекта / «Чатов»: они идут сразу под родителем, с отступом `Space.s4` на уровень. Закреплённые — как и раньше только в «Закреплённых».
- У родителя слева от точки статуса — треугольник раскрытия (`chevronRight` / `chevronDown`, 12, `text3`); клик сворачивает/разворачивает (`subsCollapsed`), строку не выбирает.
- Свёрнутый родитель вместо ветки в конце строки показывает счётчик: «2 подчата · 1 работает» / "2 sub-chats · 1 working" (вторая часть — только если кто-то работает). Слово, требующее действия («ждёт ответа» и т. п.) у самого родителя по-прежнему важнее.
- Перетаскивание: родитель тянется вместе с подчатами; подчаты сами не перетаскиваются.
- Фильтр «только ждущие» — плоский, как раньше.

## 4. Архив
Архив родителя (меню, ⇧⌘W, `sessions_archive`) архивирует и его открытые подчаты, каждый по обычным правилам (#57): worktree с незакоммиченными или игнорируемыми файлами без подтверждения не удаляется — такой подчат остаётся открытым и показывается как обычный чат верхнего уровня, пока его не заархивируют руками. `force` у MCP/CLI переходит на подчаты. Восстановление родителя подчаты не восстанавливает: они в Истории, восстановленный подчат снова встаёт под родителя. **Общий worktree (#131):** пока в папке работает другая открытая сессия, архив чата её не проверяет и не удаляет (и переопределение строки состояния остаётся) — папку проверяет и удаляет только последняя уходящая сессия. Архив родителя забирает подчаты в его же worktree с собой: одна проверка на всех (их вкладки тоже останавливаются до проверки); отказ на «рискованном» — открытыми остаются все. «Удалить навсегда» не удаляет worktree и ветку, которыми пользуется другая сессия (открытая или в архиве): уходит только запись, флажка «удалить копию» нет. Чат без проекта «засыпает», а не архивируется: сон родителя подчаты не трогает (это работа, которая идёт сама). «Убрать из списка» родителя — подчаты становятся чатами верхнего уровня.

## 5. Создание
**Из интерфейса.** «Новый подчат…» / "New Sub-chat…" — в меню строки чата (сайдбар, «⋯», палитра) и ⇧⌥⌘N для выбранного чата (рядом с ⌘N / ⇧⌘N / ⌥⌘N; свободно). Лист «Подчат для «X»»: «Что сделать» (многострочное поле, обязательно), «Агент» (Claude / Codex, по умолчанию — агент по умолчанию), «Где работать» («В папке чата» — по умолчанию, папка родителя / «В отдельной копии» — только у локального чата проекта; копия — с веткой от имени, базой по умолчанию, как `sessions_create --worktree`), подсказка «Подчат работает параллельно и ничего не передаёт чату; когда закончит, придёт уведомление.», кнопки «Отмена» / «Запустить» (⌘↩). Имя подчата — первая видимая строка задачи (#116). Ошибка (git, копия) — алерт «Не удалось запустить подчат».

**Через MCP / CLI: `sessions_spawn` / `hangar sessions spawn`.** Параметры: `name` (обязателен), `prompt` (обязателен — подчат без задания бессмыслен), `agent` (`claude` | `codex`, по умолчанию агент по умолчанию), `worktree` (новый worktree вместо папки родителя), `base` (как у `sessions_create`), `parent` (необязателен). `deliver` и `--notify-only` убраны (#131): доставки в родителя нет; старый `deliver` — `bad-params` (неизвестный параметр).

К заданию `sessions_spawn` Hangar добавляет короткую просьбу: «(You run as a Hangar sub-session. When you are done, end with a concise final result: what you found or did, key paths and links, under 1500 characters. The chat that started you may read only that last message.)» — последнее сообщение — то, что вернёт `sessions_wait` и покажет уведомление. Подчату, созданному руками, задача уходит как набрана (без приписки): пользователь читает весь чат сам (#131).

Родитель — **вызывающий чат**: `hangar mcp` и CLI читают `HANGAR_LEAF_ID` из окружения (его ставит Hangar в каждом терминале, агент и его MCP-серверы наследуют) и подставляют его в `parent`, если тот не передан. `parent` — id листа / вкладки или ссылка на сессию (id, префикс, имя). Вне терминала Hangar и без `parent` — `bad-params`. Ответ: `TaskResult` (подчат, его вкладки, `parent`) плюс `link` (`hangar://task/<id>`).

## 6. «Полностью закончил»
Статус подчата для обратной связи (`SubSessionStatus`): `still-running`, `done`, `needs-input`, `error`. Считается по агентскому листу подчата (первый лист claude/codex) чистой функцией `subSessionStatus` (`Sources/AgentStatus/SubSessions.swift`, с тестами):

| состояние листа | фоновые задачи | итог |
|---|---|---|
| ещё не работал после создания / ответа | — | `still-running` |
| `working` | — | `still-running` |
| `waiting` (разрешение, вопрос) | — | `needs-input` сразу |
| `failed`, `limit` (StopFailure, выход с ошибкой) | — | `error` сразу |
| `done` / `idle` | Stop сообщил о работающих | `still-running`; но если процессы-фоновые у агента кончились и 30 с не было хуков — `done` (Claude не разбудился) |
| `done` / `idle` | нет / неизвестно | `done`, если 5 с тишины (ни одного хука), на экране нет «esc to interrupt» и у агента нет отсоединённых детей |

Источники:
1. **Stop-хук `background_tasks`** (документация hooks, проверено 2026-11-04): массив фоновой работы сессии (`shell`, `monitor`, `subagent`, `workflow`, …) со `status`. `hangar event stop` считает записи со статусом `running`/`pending` (а без статуса — каждую) и передаёт число полем `background` (≤ 99). Нет поля (старый Claude) — неизвестно.
2. **Дерево процессов** (`Exec/ProcessProbe.swift`): дети pid агента (`agentPid` из хуков Hangar, #119), у которых своя группа процессов (`pgid == pid`, ≠ группе агента). Проверено на живом Claude Code: Bash-инструмент (и фоновый, и обычный) запускается отдельной группой (`detached`), а MCP-серверы и `caffeinate -i -t 300` — в группе claude; так серверы и caffeinate не считаются. Пробуется только для подчатов в состоянии «ждём фон», раз в 10 с.
3. **Экран**: «esc to interrupt» в последних 15 строках — агент ещё отвечает (как `codexBusy`); ловит автоматический ход Claude после окончания фоновой задачи, у которого может не быть хука в начале.
4. **Дебаунс**: любой хук листа сбрасывает таймер; когда фоновая задача заканчивается, Claude сам начинает новый ход и снова шлёт Stop с новым `background_tasks` и новым последним сообщением — `done` срабатывает один раз, после последнего тихого состояния.

Эпизод: итог (`done` / `needs-input` / `error`) отмечается один раз; когда агент подчата снова начинает работать (новый промпт от родителя или пользователя), начинается новый эпизод и следующий итог снова сообщается.

Codex: итог по `notify` (`agent-turn-complete`, `last-assistant-message`) + дебаунс + экран; фоновые процессы codex не отслеживаются (pid агента codex Hangar не знает) — ограничение.

## 7. Обратная связь
**a. `sessions_wait` / `hangar sessions wait`.** Параметры: `sessions` (список ссылок; по умолчанию — все открытые подчаты вызывающего чата), `timeout` (секунды, 1…3600). Возвращается, когда все перечисленные не `still-running`, или любой стал `needs-input` / `error`, или по таймауту (тогда у незаконченных `still-running` — вызвать снова). Таймаут по умолчанию: 110 с (Claude Code уводит вызов MCP дольше 2 мин в фон), для клиента `codex-mcp-client` — 50 с (у Codex 60 с на вызов). CLI — 110 с. Ожидание без опроса: ждущие будятся пересчётом статуса.

**b. Уведомление пользователю (#131).** В терминал родителя не печатается ничего и никогда (ни заметок, ни очереди; черновики и клавиши родителя Hangar больше не отслеживает). Когда эпизод подчата закончился с `done`, пользователь получает одно уведомление macOS «Подчат закончил» / "Sub-chat finished" с именем подчата и итогом (если уведомления включены и подчат не заглушён; не показывается, если лист подчата на экране в активном приложении). Уведомление занимает место обычного «Claude закончил» этого листа (тот же id) — одно на лист, снимается, когда лист увидели; в Центре уведомлений группируется под родителем. `needs-input` / `error` отдельного уведомления подчата не дают: их показывают обычные уведомления листа (разрешение с кнопками, вопрос, ошибка). В сайдбаре — точка статуса подчата, как у любого чата.

## 8. Результат — компактный
Контекст вызывающего агента платит за каждый символ (`sessions_wait`), поэтому итог короткий. `SubSessionInfo`: `id`, `name`, `status`, `link`, `agent`, `tab` (вкладка агента для `tabs_read`), `note` (заметка подчата `sessions_note` — где он сейчас, #133), `message` — последнее сообщение агента (Stop `last_assistant_message` / codex `last-assistant-message`; у ожидания ввода и ошибки — текст вопроса / ошибки); нет — хвост экрана (20 строк). `message` не длиннее 1500 символов: обрезанное кончается « … [truncated; full output: tabs_read]», и `truncated: true`. Чтобы было что брать: текст Stop / codex notify на границе доверия теперь хранится до 2000 символов (прочие тексты хуков — по-прежнему 500). Полный вывод — только по запросу, `tabs_read`. `sessions_list` у каждой сессии отдаёт `parent`.

## 9. Вне рамок
Подчаты на удалённых проектах (родитель по ssh): `sessions_spawn` работает (подчат того же проекта), но фоновые процессы на сервере не пробуются — только `background_tasks` и дебаунс. Отмена/остановка подчата из родителя — существующие `tabs_send keys [interrupt]` и `sessions_archive`.
