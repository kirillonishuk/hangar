# Hangar — правила для агентов

Hangar — нативное macOS-приложение (Swift, AppKit + SwiftUI), замена Pane (Electron): рабочее место для AI-агентов (Claude Code, Codex) во вкладках терминала libghostty (GhosttyKit). Структура: проект → задача (worktree опционален) → вкладки. Плюс дерево файлов, read-only diff, вкладки Helix, статусы агентов, лимиты подписок, восстановление сессии, CLI `hangar` + MCP.

Источники правды (читать нужный раздел, не всё подряд):
- Спека: `docs/superpowers/specs/2026-10-18-hangar-design.md`
- Решения и открытые вопросы: `docs/decisions.md`
- Дизайн-система: `docs/design/DESIGN.md`
- Макеты: `docs/superpowers/mockups/` (`style-a-v2.html`, `new-task-v4.html`, `limits.html`, `icons-sidebar.html` (иконки + свёрнутая рейка) — эталон; `style-a-screens.html` — устаревшая раскладка, только уведомление)

## Не ходить по кругу
- Спека и `decisions.md` обязательны. Решённый вопрос не переоткрывать без новой информации (факт, ошибка, слово пользователя).
- Изменилось поведение или рамки → в том же коммите обнови спеку или добавь запись в `decisions.md`.
- Не уверен → задай пользователю один конкретный вопрос. Не исследуй альтернативы «на всякий случай».
- Работай по одному этапу из §11 спеки. Следующий — только когда текущий готов.
- «Вне рамок» (§1 спеки) соблюдается: git-действия, браузер, свой редактор, онбординг, синк, Linux/Windows — не делать и не закладывать.

## Оркестрация (экономия контекста)
- Основная сессия — только оркестратор: читает план, выдаёт задачи, принимает отчёты, решает, общается с пользователем. Сама код не пишет и большие файлы/логи не читает.
- Каждую задачу плана делает свежий сабагент-исполнитель; ему передаётся текст задачи, Interfaces соседних задач и ссылки на нужные разделы спеки — не весь контекст.
- Результат каждого исполнителя проверяет второй, независимый сабагент-ревьюер (сверка со спекой/планом, тесты запущены, порядок ревью из «Простоты»). Без «ок» ревьюера задача не закрыта; замечания — снова исполнителю.
- Отчёты сабагентов — короткие: что сделано, команды проверки и их результат, коммит, риски. Без дампов кода и логов.
- Исследования «по всему коду» — тоже через сабагента; в основную сессию приходит вывод, не файлы.
- Исключение: действия, требующие согласия пользователя (установка, изменения его файлов), — оркестратор сначала спрашивает пользователя, потом поручает.

## Простота
Бери первый вариант, который полностью работает:
1. Нужно ли это вообще? Не просили — не делай, назови одной строкой.
2. Уже есть в проекте? Используй так же, как окружающий код.
3. Есть в Foundation / AppKit / SwiftUI / системе? Используй: `Process` + `git` CLI (не libgit2), FSEvents (не опрос), `UserNotifications`, `Codable` + JSON, `NSPopover`, системные контролы.
4. Иначе — минимум нового кода. Новая зависимость — последнее средство и только с записью в `decisions.md`. Никаких сторонних UI-китов.
- Без абстракций, протоколов с одной реализацией, опций и кода «на потом». Удаление лучше добавления.
- Ленивое решение, но полное изменение: доделай вызывающих, тесты, конфиг, которые задевает правка.
- Баг: найди всех вызывающих и чини корень в общем коде один раз.
- Нетривиальная логика (ветвление, парсер, запись данных) — хотя бы один тест.
- Сознательное упрощение — комментарий `shortcut: <ограничение>, <когда менять>`.
- Комментарии — только «почему», одной строкой.
- Никогда не урезать: валидацию на границах доверия (сокет, hooks, stdin), защиту от потери данных, безопасность, доступность, то, что пользователь просил.
- Ревью — по порядку: корректно, безопасно, тестировано, быстро/экономно, без лишнего. Находка без конкретного сценария поломки — не находка.

Принципы простоты адаптированы из ponytail (MIT, DietrichGebert).

## Экономия токенов и времени
- Читай точечно: `grep`/`rg`, диапазоны строк. Не перечитывай только что отредактированный файл.
- Не выводи большие файлы и логи целиком — фильтруй.
- Никаких рефакторингов «заодно». Маленькие файлы с одной задачей.
- Ответы короткие: что сделано, что не проверено, риски.

## Инженерные правила
- Границы модулей — §2 спеки. Только `GhosttyBridge` трогает C-API GhosttyKit. `Workspace`, `Git`, `AgentStatus` — без UI-импортов и с юнит-тестами.
- Энергия: в простое ноль таймеров и опросов; скрытые surface на паузе рендера; файловые изменения — FSEvents + debounce, только для видимой задачи.
- `~/.claude`, `~/.codex`, конфиг Ghostty и прочие файлы пользователя — менять только с явного согласия (показать diff, сохранить исходное для отката).
- Разрушительные операции: CLI — `--yes`, MCP — `yes: true`, иначе отказ.
- Горячие клавиши `⌘…` сопоставлять по `keyCode`, чтобы работали в русской раскладке.
- UI — по `docs/design/DESIGN.md` и макетам; цвета/размеры только из `Theme`, не литералами.
- Ничего не устанавливать (brew, плагины, npm) без согласия пользователя.

## Готово, когда
- Собирается; тесты логических модулей проходят (запуск показан, а не предполагается).
- Спека / `decisions.md` обновлены, если менялось поведение.
- UI сверен с макетами и `DESIGN.md`.
- Коммит с понятным сообщением (`feat:`, `fix:`, `docs:` …).

## Общение
Отвечай пользователю по-русски. Идентификаторы, код и команды — как есть.
